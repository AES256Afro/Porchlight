# Porchlight

An attack-surface monitor (Cloudflare Worker, `monitor/`) and a repository scanner with a monitor client (Node CLI, `cli/`), which also checks the computer it runs on, investigates proven domains and audits the owner's Cloudflare account. `README.md` covers usage. This file covers what must stay true.

## Commands

- `npm run check` and `npm test` at the root cover both packages.
- Monitor: `npm run dev`, `npm run db:migrate:local`, `npx cf deploy --dry-run` (builds and validates; needs no login).
- Mac app: `sh mac/build.sh --install` builds one for this machine. `sh mac/build.sh --dmg` builds the download attached to a release: the CLI from the last commit, never uncommitted changes, plus copies of `node`, gitleaks and osv-scanner with their licences. The DMG must hold nothing of the machine that built it (no path, name, setting or token), and each bundled program must link only to macOS's own libraries; the script checks the latter. Search a mounted DMG for the owner's paths and names before attaching it to a release.
- Cloudflare work goes through the `cf` CLI and `monitor/cloudflare.config.ts`. Do not add Wrangler or a Wrangler config file.

## Invariants

Do not weaken these without the owner asking for it.

1. **Ownership gate.** No request is made about a domain (certificate log, DNS other than the challenge record, HTTPS) unless `checkOwnership` passed earlier in the same scan. The "ownership gate" tests in `monitor/test/scan.test.ts` assert on the exact request list.
2. **Passive only.** One `GET /` per host, no redirects followed, no port scanning, no guessing of subdomains or paths. This binds the monitor and every scan. The one exception is an investigation the owner starts and approves step by step (invariant 20).
3. **Secrets stay in the scanner.** gitleaks always runs with `--redact`. Reports never carry secret values, matches, author names or emails.
4. **The API fails closed.** A missing or short `ADMIN_TOKEN` makes every `/domains` route answer 503.
5. **"Not observed" is not "empty".** A failed lookup is stored as `null` or a missing key. It must never be reported as a change or clear a finding.
6. **The CLI has no runtime dependencies.** It runs TypeScript directly through Node's type stripping, so use erasable syntax only and `.ts` import extensions. The web interface in `cli/ui/` follows the same rule: plain JavaScript and CSS, no framework, no build step.
7. **The web interface answers only its own page.** `cli/src/ui/server.ts` binds 127.0.0.1 by default, rejects any other Host or a cross-site Origin, and requires the session key on every `/api` call. The monitor's admin token is added server-side and never sent to the browser. It is given at start-up or typed once under Settings → Monitor (`cli/src/monitor/settings.ts`): only on the loopback page, never as a service or from another device; the address must be https (or this computer) and is kept as its origin alone; the monitor is asked with the token before anything is saved, so a mistake never replaces a working connection; both are kept 0600 in `monitor-settings.json`, the token goes only to that address as the Authorization header, and error text never carries it. Listening on any other address (the BoxPilot container) needs a fixed `PORCHLIGHT_UI_KEY` of at least 32 characters or the server refuses to start; it then accepts any well-formed Host, still compares the Origin's host, and never prints the key. "Access from other devices" (Settings) adds a second listener on the Tailscale address only (100.64.0.0/10, never 0.0.0.0), with its own generated access key (kept 0600 in `access.json`); each listener accepts only its own key. Only the loopback page can turn it on or off or see or replace the key, and a service never opens it.
8. **No HTML is built from data.** Finding titles, file paths and DNS values are attacker-controllable, so `cli/ui` builds every element with `h()` in `dom.js` and never uses `innerHTML`. The Content-Security-Policy forbids inline script and style; keep both in files.
9. **The BoxPilot manifest matches the image.** `boxpilot/porchlight.yaml` keeps `defaultExposure: tailnet`, a read-only repos mount and a generated key; `npm run check:boxpilot` checks it against the Dockerfile and BoxPilot's schema. The image is published only from a `v*` tag by CI, after `scripts/container-smoke.sh` passes.
10. **Triage re-ranks; it never drops.** `cli/src/repos/triage.ts` lowers a secret's severity one step per reason (a generic rule, an unlikely path) and records the reason in the finding's `note`. Do not turn it into a filter: a real key can live in a test file. Path rules match whole segments and file-name conventions, never substrings.
11. **Exports are escaped for their format.** Everything a roadmap or findings export prints from a scan goes through `cli/src/roadmap/escape.ts`: entities in HTML, an apostrophe before formula characters in CSV, escaped text or fenced code in Markdown. The HTML export has no script and loads nothing. Download names are built from a fixed stem and a date, never from request input.
12. **A suggested fix is the complete repair.** The fix shown for a finding is planned from its whole repository, not from whatever a filter left on show, so following it clears every advisory against the package. An export of part of a scan says it is partial; one from an incomplete scan says what was not covered.
13. **A model sees only what the page shows, as data, and never decides anything.** This holds for every model: Ollama, a server of the owner's that speaks OpenAI's format (`compatible`, such as Unsloth Studio or LM Studio), or a hosted one (Claude, OpenAI, Gemini, DeepSeek; `cli/src/assist/ollama.ts`). `cli/src/assist/prompts.ts` sends only fields the page displays, built by the server from its own copy of the report (the request only names what to explain), as one framed JSON block the model is told is data, not instructions. Never secret values, authors, emails, the admin token or a domain's challenge. Its output is labelled as generated with the model's name (`generatedText` in `cli/ui/assist.js`), rendered as text with `h()`, never as HTML, and never acted on. The one place a model proposes an action is an investigation, and there plain code decides whether it runs (invariant 20). A hosted provider's address is fixed in the code, its key reaches only that address as a header and never a log or a report, and the page says before anything is sent that it leaves the owner's machines. The model can be chosen in Settings → Model (`cli/ui/models.js`, `cli/src/assist/settings.ts`): the server takes the provider from that list, never from a request. A key typed there is sent once to Porchlight's own server, kept in `model-settings.json` (0600) beside the report, and never sent back to the page. Keys are kept per provider, and a key for the owner's own server only with the address it was saved for.
14. **A scanned repository is hostile input.** Its own configuration never runs code or changes what is detected. gitleaks runs with `GITLEAKS_CONFIG` and `GIT_LOG_OPTIONS` (`cli/src/repos/gitleaks.ts`), never with the repository's `.gitleaks.toml` or the diff programs its `.git/config` names; the container trusts only `/repos/*`. Ignore files it carries (`.gitleaksignore`, `osv-scanner.toml`) are honoured but named in the report (`settingNotes`). A scanner that reports nothing because it could not read the repository has failed, and that is never a clean result. The hostile-repository tests in `cli/test/scan.test.ts` and step 4 of `scripts/container-smoke.sh` check this.

15. **Fetching from GitHub contacts GitHub only, and its token goes nowhere else.** `cli/src/github/github.ts` builds every address from an owner and a repository name that match GitHub's naming rules; nothing from a request is used as an address or a path. The token reaches api.github.com as a header and git through its environment (`gitEnv`), never an argument, a URL, a repository's configuration, a report, a log or the browser, and error text is scrubbed of it. Every git command carries `GIT_SAFE_ARGS` (no hooks, submodules, symbolic links, credential helpers or redirects; https only) and ignores the user's and the system's git settings. Fetched repositories live beside the report, are scanned as a further root (`otherRoots`, named `github/<owner>/<repository>`), and are hostile input like any other.

16. **The model's analysis is advice beside a finding, never a change to it.** `cli/src/analysis/` has a model judge findings (a package's advisories together, a secret alone) from evidence Porchlight reads itself: how the package is declared and which of the repository's own lines import it (`evidence.ts`: read-only, no git, no symbolic links, only lines naming the package, cut short). A secret gets no file content at all, since the lines around a secret may hold it. The page shows that evidence beside the judgement, so invariant 13 still holds. Judgements live in their own file beside the report (`repo-analysis.json`), tied to one scan; they never alter a severity, a count, the roadmap, an export or the CLI's exit code, and "unlikely" only sorts last. An answer that is not the JSON asked for becomes "unclear". The one place a model's words enter an export is the mural, and only when asked for (`cli/src/assist/mural.ts`): its own section, labelled with the model's name, escaped for the format, beside figures Porchlight counts itself; it never changes the export's findings, counts or roadmap. Its prompt carries counts, roadmap actions, the titles of findings judged real and of findings fixed since the last scan (as the Overview lists them), never a reason, evidence or a secret's details.

17. **History and the owner's notes sit beside findings, never in them.** `cli/src/repos/history.ts` keeps each finished scan (0600, under `history/`, last 50) and counts new and fixed by `findingKey` (`cli/ui/tracking.js`, shared by page and server). A finding counts as fixed only where the later scan looked again (its scanner ran and did not fail on that repository) and as new only where the earlier one had looked; the rest is counted as "could not be checked again", never as fixed (invariant 5); `finding-notes.json` (0600) holds the owner's status and note per finding. Neither changes a severity, a count, the roadmap, an export or the exit code, and a status never hides a finding. A kept scan is read only by a name from the index, never a path from a request. The page's place (`ui-view.json`) is saved without the session key.
18. **"Send to a model" names, it never supplies.** `POST /api/repos/send` takes a model by Porchlight's own id (`sendTargets` in `cli/src/assist/settings.ts`: the models set up in Settings or at start-up, keys never sent to the page), a content, a purpose and the page's filter; `sendPrompt` builds the data from the server's own report under invariant 13. The answer is shown as generated text, copied or saved as plain text under a fixed name, and never acted on.

19. **The host check only reads.** `cli/src/host/` runs the system's own tools through the injected `Runner`, each with a time limit: no shell, no `sudo`, no command that changes a setting, nothing that contacts another machine on the network. Asking Apple for updates and OSV.dev for installed packages' advisories are page options, and the page says what they send. A credential file is read only to say that it holds a credential, which kind, and who can read it; its contents are never kept, returned, logged or shown (invariant 3). A check that could not run, or whose answer is not recognised, is `unknown` and shown as "Could not check", never as passed (invariant 5). The result is `host-check.json` (0600) beside the report. A model, if this is ever sent to one, sees only what the page shows (invariant 13). As a service it refuses to run: a container cannot see its host. The combined "Commands to fix these" (`combinedCommands` in `cli/ui/host-areas.js`) hold only commands safe to paste without a decision: package names that match a strict pattern, file names quoted with `shellWord`, and never a step that could cut off access or break a script (turning off a Sharing service, adding a passphrase to a key).

20. **An investigation acts only on a proven domain, and only through fixed tools.** `cli/src/investigate/` lets a model propose one action a turn; code decides. The domain's `_porchlight-challenge` TXT record must hold its token (a record published before the rename, under `OLD_CHALLENGE_LABEL`, still counts) (`ownership.ts`, a DNS-over-HTTPS lookup from this computer; the monitor's token is adopted when it has one, otherwise one is made and kept 0600 in `investigate-domains.json`) when the run starts and again before every action; a failed lookup stops the run, never passes it (invariant 5). Scope is that domain and its subdomains (`scope.ts`), names only, never an address. The tools (`tools.ts`) are DNS over DoH, one `GET`/`HEAD`/`OPTIONS` with no redirects, and one TCP connect; there is no shell and never will be. Arguments are checked strictly and refused, never repaired. Each host is resolved once and the connection goes to that address; a private, loopback, link-local or CGNAT address is refused. HTTP and TCP wait for the owner's approval on the loopback page, showing the exact tool and arguments; Stop works from anywhere. The owner may instead approve the rest of one run at once (`approvedRest`), when starting it or at any request: only on the loopback page, only for that run, never remembered for the next, and only after the page has listed what the run may send (`runLimits` in `cli/ui/hints.js`, from the server's own tool list). That lifts the wait and nothing else: the scope, the ownership check before every action, the argument checks, the gap and the turn budget hold, and each step records which approval let it run (`approvedBy`). Asking before each request is the default, and an answer that is not a plain yes, or a yes to the rest, is a denial. At least `minGapMs` (1 s) between actions on a host, and a turn budget (25, at most 60). Tool output reaches the model only inside `<tool_output>` tags with any such tag in it broken (`fence`), Set-Cookie values left out, and never the ownership token. A finding is kept only if every evidence id it cites was captured in this run. Findings are labelled as the model's, accepting or dismissing one is recorded with the run, and none changes a scan's severity, count, roadmap, export or exit code. A hosted model is used only after the page has said what is sent and the owner said yes (`sendsToHosted`): the page shows what is sent above a start button that names the model, and pressing it is the yes, with no separate box to tick; a request that does not say so is still refused. Runs are kept 0600 under `investigations/`, read only by an id matching `inv_` and 16 hex digits. Exports escape for their format (invariant 11). Tests (`cli/test/investigate*.test.ts`) use a scripted model and network.

21. **The Cloudflare audit reads with the owner's token, and changes only what the owner approves.** `cli/src/cloudflare/` reads the owner's Cloudflare account through an API token pasted under Settings → Cloudflare (or `PORCHLIGHT_CLOUDFLARE_TOKEN`). The token is checked with Cloudflare before it is saved, kept 0600 in `cloudflare-settings.json` beside the report like the model keys, and sent only to the fixed `CLOUDFLARE_API` (`client.ts`) as the Authorization header: never in an address, a log, a report, an export, the page or a model, and error text is scrubbed of it. Paths are fixed templates with 32-hex-digit IDs; nothing from a request becomes an address. The rules (`rules.ts`) are plain code, no model, and know each zone's plan: a feature the plan lacks is `unavailable`, never a fault; a read the token was refused is `unknown` ("Could not check", naming the permission), never passed (invariant 5). The audit only reads, apart from one lookup: the names a zone's CNAME records point at outside the account are looked up over DoH only for a zone whose `_porchlight-challenge` record holds this computer's token, checked earlier in the same audit (invariant 1). Members appear only as a masked email. The default is read-only. A change is one of the fixed templates in `apply.ts` (the ownership record, or one of five zone settings), offered only for a problem the latest audit found in that zone; the page shows the exact request (method, full address, body, the header as "not shown") and only the owner's approval on the loopback page sends it, once, within 10 minutes. "Fix these" (`planBatch`) shows every such request for one zone or all of them and sends them after one approval: the same templates, chosen by the audit and never by a request or a model, each sent once in order; the owner may leave some out but nothing can be added, a permission the token lacks is found once and the rest that need it are not sent, and Stop leaves what was sent in place. Nothing is ever applied automatically. Every change sent, accepted or refused, is recorded 0600 in `cloudflare-changes.json`. The audit is kept 0600 in `cloudflare-audit.json`; exports escape for their format (invariant 11). A model's analysis follows invariant 13: it reads the stored audit as the page shows it, without members, token names or ownership values, and changes nothing. Tests (`cli/test/cloudflare*.test.ts`) use the fake account in `cli/test/cloudflare-fake.ts`.

22. **A discussion keeps a model's answers beside the findings, and a follow-up adds nothing but the owner's question.** Every answer from Explain, Summarise, Ask, Send to a model and the Cloudflare analysis is kept as a discussion (`cli/src/discussions/`, 0600 under `discussions/`, the last 200, read only by an id matching `dsc_` and 16 hex digits). It records what was asked about, the model and where it ran, the owner's questions and the answers; never a key, a token or a secret value, and the page is sent no address of the model beyond its host. Its title is Porchlight's, made from what was asked about, never the model's words. A follow-up goes only to the model the discussion began with (the same id, and the same provider, address and model, so never one swapped in since) and only while the scan it was about (or, for the Cloudflare analysis, the audit) is still the latest. The server rebuilds the first prompt from its own data (invariant 13), then sends the earlier answers as the model's own turns and the owner's question after a fixed reminder that the data is not instructions. A model on the owner's machines gets at most `LOCAL_HISTORY_CAP` characters of earlier answers, the oldest dropped first and the page told, so Ollama never trims the rules at the start of the prompt. Answers are shown as generated text and never acted on, and no discussion changes a severity, a count, the roadmap, an export's findings or the exit code. Exports escape for their format (invariant 11).

23. **A project folder is the owner's, and Porchlight writes only inside its `Porchlight` subfolder.** `cli/src/projects/projects.ts` writes saved exports, discussion transcripts and a daily log there, and nowhere else. A file's name is the date, the time and a title from `FILE_TITLES`, never anything from a scan, a request or a model's answer (invariant 11). A file is created new (`O_EXCL`, `O_NOFOLLOW`; a second in the same minute gets " 2") and never written over, except a discussion's own transcript, which is replaced through a new file renamed over it. A link or a file where one of Porchlight's own folders should be is refused, checked on every write, and a chosen folder that has gone is never made again. Folders are 0700 and files 0600. The log holds Porchlight's own words and figures: never a key, a token, a secret value, an email, the owner's questions or a model's text, and nothing in an event can start a new line. A folder is checked and shown (`GET /api/projects/preview`) before it is saved, with a warning, not a refusal, when it is inside a git repository or a scanned folder. Projects are added and removed only from the page on this computer or a service's own page (whose folders must be inside `projects` in its data folder, checked before anything else is looked at); another device over the tailnet can only move between them. Removing a project leaves its folder as it is. The Mac app's bridge (`mac/Porchlight.swift`) answers only its own page's main frame: it hands back a folder the owner picked and nothing else, and shows in Finder only an existing path inside a folder named `Porchlight`. Nothing in a project changes a severity, a count, the roadmap, an export's findings or the exit code.

## Interface conventions

- The Activity view (`cli/ui/activity.js`, `note()` in the server) shows what Porchlight is doing as it happens: the last 400 lines, in memory only. Like the project log it holds Porchlight's own words and figures, one line each: never a key, a token, a request's body, a secret value or a model's text.

- A look (Settings → Appearance, `cli/ui/looks.js`) restyles or moves what a page shows. It never hides a finding, changes a count or drops the "Not covered" banner. The server accepts only the looks in that list.
- Where a model's answers appear (`ANSWER_PLACES` in `cli/ui/looks.js`: the answers panel on the right, below what was asked about, or a drawer at the bottom) only moves them. The panel (`cli/ui/panel.js`) sits outside the page, so it stays open between pages, and the page makes room for it rather than going under it; on a narrow screen it covers the page until closed. Like a look, it never hides a finding, and the server accepts only the places in that list.
- A severity is always shape, colour and word together (`severityBadge`), never colour alone. Status colours mark state only; text stays in the ink colours.
- An incomplete scan is shown as incomplete (the "Not covered" banner), never as clean.
- An empty page says what to do next. What a scan would cover is asked from the server (`GET /api/repos/preview`) and shown before anything runs; the words for "nothing here yet" and for setting up the monitor live in `cli/ui/hints.js`, written for a terminal and for a service (BoxPilot) separately, and are tested without the DOM. A folder is looked into only once its box is settled, never on each keystroke.
- `cli/ui/filter.js` decides what a filter matches, for the page and for the server alike, so "export what the filters show" exports exactly that. Do not filter anywhere else.
- A page's filters, order and page number live in the address (`cli/ui/list.js`), written with `history.replaceState`, so reload, back and shared links restore the view.
- Pages read shared data from `cli/ui/store.js` and subscribe to it; they do not fetch the report themselves. Long lists are paged, not rendered whole.
- A click path in the page's words ("Settings → Model", "System Settings → Network → Firewall", GitHub's settings) is written the same in every string and listed in `cli/ui/paths.js`, which `stepNodes` turns into breadcrumbs, linking each step that has a fixed address of its own (Porchlight's own page, github.com, or a System Settings pane, the last only when the page is shown on the Mac itself). A test fails on any path the page or the host check writes that is not listed. The Mac app opens only http(s) and `x-apple.systempreferences:` links outside its window.
- Browser code is typed with JSDoc and checked by `npm run typecheck`. It imports its data types from the TypeScript sources.

## Testing

- Tests never touch the network. The monitor injects `Deps` (`fetch`, `now`) and tests pass `fakeDeps` from `monitor/test/fake-net.ts`. The CLI injects a `Runner` and tests pass `fakeRunner`; the UI server takes a `fetchFn` for the monitor, the local model, GitHub and Cloudflare, and a `run` for git, and tests pass fakes for all of them. A Cloudflare token for tests is assembled at run time (`fakeCloudflareToken`).
- Secret-shaped test data is assembled at run time (`fakeAwsKeyId` in `cli/test/helpers.ts`), so this repository's own pre-commit secret scan has nothing to find. Do not commit literal credential-shaped strings.
- `cli/test/fixtures/osv-scanner-2.7.1.json` is real osv-scanner output, trimmed. When the tool's format changes, capture a new fixture instead of editing this one by hand.
- osv-scanner exits 127 with an empty, well-formed report when it cannot reach its database. Treat any exit code other than 0, 1 and 128 as a failure, never as "no vulnerabilities".
